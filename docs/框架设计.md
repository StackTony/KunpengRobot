## 1. 项目概述

鲲鹏运维平台（KunpengRobot），Python 实现的 Web 运维平台：

- **部署环境**: Linux / Windows 均支持，ARM (aarch64) / x86 双架构
- **访问方式**: Web 端 (浏览器)
- **核心功能**:
  1. 用户权限控制 (JWT + RBAC，如普通用户/管理员)
  2. 故障诊断日志分析 (优先)
  3. 智能巡检 (优先)：规则匹配打底 + LLM 智能总结
  4. 巡检规则管理：管理员对规则增删改查
  5. 性能数据图表：数据持久保存，切换页签/刷新页面不丢失
  6. 预留扩展能力
- **用户规模**: ~1000 用户，每秒并发上传约 100+ 次，后续可能增长
- **日志来源**: 被动上传模式 —— 用户通过"一键收集命令"在目标服务器收集日志包后上传到平台分析

## 2. 总体架构

```
┌──────────────────────────────────────────────────────┐
│            浏览器 (Vue3, SSE/WS 客户端)               │
└───────┬──────────────────────────┬───────────────────┘
        │ 1. 上传日志包(REST)        │ 2. 订阅任务进度(SSE)
┌───────▼──────────────────────────▼───────────────────┐
│         Nginx (上传缓冲 client_body_temp, 反代)        │
├──────────────────────────────────────────────────────┤
│   API 服务 ×N (FastAPI, 多进程, 无状态, 可横向扩)      │
│   认证/RBAC · 上传接收 · 任务管理 · SSE/WS 端点        │
└───────┬──────────────────────────┬───────────────────┘
        │ 3. 任务入队               │ 6. 订阅事件通道
┌───────▼──────────┐        ┌──────▼──────────────────┐
│      Redis       │◄───────┤   事件流                 │
│ · Stream 任务队列 │  5.发布 │ · Pub/Sub 实时推送       │
│   (消费组+ACK+重试)│  进度  │ · Stream 事件留存(断线补发)│
│ · 令牌黑名单/限流  │        │ · worker→API→浏览器      │
└───────┬──────────┘        └────────▲──────────────────┘
        │ 4. 消费任务                  │
┌───────▼────────────────────────────┴─────────────────┐
│   分析 Worker ×N (独立进程, 可横向扩)                  │
│   解压校验 → 格式识别 → 解析器插件 → 规则引擎 → LLM    │
│   · asyncio 驱动全流程 (LLM 调用异步流式)              │
│   · CPU 密集的解析走 ProcessPoolExecutor              │
│   · 每步进度/中间结论 → 事件通道 (打字机式实时输出)     │
│   · APScheduler 也在 Worker 进程触发巡检任务入队       │
└───────┬──────────────────────────────────────────────┘
        │
   PostgreSQL (用户/角色/任务/报告元数据) + 本地/共享存储 (日志包/报告)
```

**核心数据流**: 被动上传 → 入队即返回 task_id → Worker 并发异步分析 → 全程进度经 Redis 事件通道 → SSE 流式回推浏览器。

## 3. 技术栈

| 层 | 选型 | 说明 |
|---|---|---|
| 后端框架 | FastAPI (Python 3.11+) | API 与 Worker 共用代码库，不同启动入口 |
| Web 服务器 | Uvicorn；Linux 可选 gunicorn 多 worker | API 无状态可多进程/多机 |
| ORM/迁移 | SQLAlchemy 2.0 (async) + Alembic | |
| 数据库 | PostgreSQL | 元数据：用户/角色/权限/任务/报告/规则 |
| 时序数据 | PostgreSQL 时间分区表 (起步) | 性能指标存储；量大后 Linux 可平滑加 TimescaleDB 扩展 |
| 缓存/队列/事件 | Redis 5+ | Stream 任务队列 + Pub/Sub + Stream 事件留存 + 限流/黑名单 |
| 前端 | Vue 3 + Element Plus + Vite + Pinia + ECharts | |
| 认证/权限 | JWT + RBAC (用户-角色-权限三级) | 令牌黑名单放 Redis |
| 任务调度 | APScheduler (AsyncIOScheduler, SQLAlchemy jobstore) | 在 Worker 进程触发巡检任务入队，重启不丢调度 |
| 智能分析 | 规则引擎 + LLM 混合 | 规则打底，LLM 根因分析与建议，可降级纯规则 |
| LLM 接入 | openai SDK (OpenAI 兼容 API，可指向本地模型) | 流式响应逐 token 转发 |
| 实时推送 | SSE (sse-starlette) 为主 | 单向流轻量、自动重连；未来双向交互再补 WebSocket |

## 4. 模块设计

### 4.1 用户权限 (RBAC)

- 用户 - 角色 - 权限三级模型
- JWT 认证；刷新令牌/登出黑名单存 Redis，避免每请求查库
- 上传/分析接口按用户维度限流 (Redis 计数)

### 4.2 故障诊断日志分析

分析流水线，解析器插件化保证不同日志格式可扩展：

```
日志包上传 (zip/tar.gz)
  → 入队 (Redis Stream), 立即返回 task_id
  → Worker 消费: 解压 & 安全校验
  → 格式识别 (按服务器类型/特征指纹)
  → 匹配解析器插件 (每种日志格式一个 parser, 注册制接入)
  → 结构化提取 (时间/级别/组件/关键字段)
  → 规则引擎匹配 (正则模式库 + 阈值, 命中即产生告警条目)
  → LLM 根因分析 (规则命中结果 + 关键日志片段送入大模型,
    流式输出诊断结论与处置建议; 无 LLM 时降级为纯规则报告)
  → 生成诊断报告 (可下载)
```

- 新增日志格式 = 新增一个 parser 插件 + 对应规则集，不动核心代码
- 全流程每步进度/中间结论实时推送 (SSE)，用户看到打字机式输出
- 断线重连: 事件写 Redis Stream (带 TTL)，重连先补发历史再续流

### 4.3 智能巡检

- 巡检模板: 按服务器类型定义检查项集合 (CPU/内存/磁盘/服务状态/关键日志错误等)
- 检查项插件化: 每个检查项独立检查器，便于扩展
- **分析策略: 规则匹配优先 → LLM 智能总结**。先由规则引擎产出确定性命中结果（快、可解释、可离线），再将命中结果与关键上下文交由 LLM 生成总结与建议（无 LLM 时降级为纯规则报告）
- 定时调度: APScheduler 周期触发，任务同样走 Redis 队列 → Worker 执行
- 巡检进度实时推送，报告含健康评分 + 异常明细 + 历史趋势
- 与诊断模块复用同一套规则引擎和 LLM 接入层

### 4.4 规则管理 (管理员)

- 规则为数据库实体，管理员通过界面增删改查，普通用户只读
- 规则结构: 规则名/描述、匹配类型（正则/关键字/阈值）、适用日志类型与服务器类型、严重级别 (info/warn/error/critical)、启用状态、优先级
- 规则校验: 保存前校验正则合法性、防灾难性回溯（超时/复杂度检查）
- 规则变更审计: 记录操作人/时间/变更内容
- 生效机制: 规则版本化存储，Worker 通过版本号感知变更并热加载，无需重启
- 内置一批预置规则 (常见故障模式)，管理员可基于其扩展

### 4.5 性能数据与图表

- **数据来源**: 日志包解析出的性能指标 (如 sar/监控日志中的 CPU/内存/磁盘/网络数据)、巡检检查项采集的指标，统一抽取为时序点入库
- **存储**: PostgreSQL 时间分区表 (按月/周分区 + 时间 BRIN 索引)，保留期可配置 (如 90 天)，APScheduler 定期清理过期分区
- **图表 API**: 按主机/指标/时间范围聚合查询 (raw + 降采样)
- **前端图表**: ECharts，支持多指标对比、时间范围选择
- **持久化策略 (刷新/切页签不丢失)**:
  - 数据层: 指标持久存于服务端，页面加载时按查询条件重新拉取，天然不丢
  - 配置层: 用户的图表布局/所选指标/时间范围等视图配置保存到服务端 (用户偏好表)，刷新或换设备登录后恢复
- 扩展路径: 数据量持续增长时，Linux 环境可平滑启用 TimescaleDB (PG 扩展，压缩与自动分区)，应用代码几乎不变

### 4.6 任务可靠性

- Redis Stream 消费组: ACK 确认、pending 重投、Worker 崩溃任务不丢
- 任务状态机: pending → running → done/failed/cancelled/interrupted
- 任务元数据落 PostgreSQL，进程重启后 interrupted 任务可重新下发

## 5. 并发与扩展模型

| 层 | 模型 | 扩展方式 |
|---|---|---|
| API 层 | Uvicorn 多 worker (Linux 可 gunicorn) | 无状态，加机器即可 |
| Worker 层 | 多进程消费同一队列 | 线性加 Worker 进程/容器 |
| 日志解析 | CPU 密集 → ProcessPoolExecutor | 进程池大小按 CPU 核数调 |
| LLM 调用 | IO 密集 → asyncio + 并发上限 + 限流 | 调大并发上限/多 Worker |
| 事件推送 | Redis Pub/Sub 扇出 | API 层各自订阅，天然支持多实例 |

**容量评估**: 1k 用户 / 100+ QPS 规模，2C API 实例 + 2~4 Worker + 单 Redis + 单 PostgreSQL 可从容支撑，增长时线性加 Worker。

## 6. 部署方式 (两套，均支持 ARM/x86)

| 组件 | 裸机部署 | Docker Compose |
|---|---|---|
| Nginx | systemd (Linux) / NSSM (Windows) 服务 | 容器 |
| API 服务 | systemd / NSSM 守护 Uvicorn | 容器 (`--scale api=N`) |
| 分析 Worker | systemd / NSSM 守护独立进程 | 容器 (`--scale worker=N`) |
| Redis | systemd / NSSM 服务 | 容器 |
| PostgreSQL | systemd / NSSM 服务 | 容器 |
| 镜像架构 | — | `docker buildx` 出 `linux/amd64` + `linux/arm64` 双架构 |

- `deploy/` 目录提供: Linux 安装脚本、Windows NSSM 注册脚本、docker-compose.yml
- Nginx 需配置: 上传体积上限、`client_body_temp` 缓冲、SSE 反代 (`proxy_buffering off`、长超时)

### ARM/x86 兼容性

全部 Python 依赖在 PyPI 均有 aarch64 wheel，无 x86-only 依赖，代码层面零差异；Docker 镜像双架构构建。

## 9. 设计决策记录

| 决策 | 结论 | 理由 |
|---|---|---|
| 前后端分离 | 是 | Vue3 SPA + FastAPI REST |
| API 与分析解耦 | 是 | 100+ QPS 上传不能被分析拖慢，入队即返回 |
| 队列选型 | Redis Stream 消费组 | ACK/重投保可靠，避免引入 Kafka/RabbitMQ 重依赖 |
| 事件通道 | Redis Pub/Sub + Stream 留存 | 跨进程实时推送 + 断线补发 |
| 实时推送协议 | SSE 为主 | 单向流、自动重连、过代理友好 |
| 智能方式 | 规则引擎优先 + LLM 总结 | 规则打底可离线可解释，LLM 增强总结，可降级 |
| 规则存储 | 数据库实体 + 版本化 + 热加载 | 管理员界面 CRUD，Worker 不重启即生效 |
| 时序指标存储 | PostgreSQL 时间分区表 | 裸机需支持 Windows（TimescaleDB 无 Windows 原生支持）；量级起步够用，量大后 Linux 可平滑升级 TimescaleDB |
| 图表持久化 | 指标服务端存储 + 用户视图配置落库 | 刷新/切页签重新拉取即恢复，不依赖前端内存状态 |
| 日志格式扩展 | 解析器插件注册制 | 新格式不改核心代码 |
| 采集方式 | 被动上传 | 用户侧一键收集后上传，平台不主动 SSH |
| Celery | 不用 | 进程模型重，流式事件回传困难，Redis Stream + asyncio 足够 |
| 单库双入口 | API/Worker 共用代码库 | 部署形态不同，业务代码共享 |
